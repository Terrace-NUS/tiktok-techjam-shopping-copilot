# 总评：核心故事有决赛乃至争冠辨识度，但目前还是“半闭环”

你们现在最有价值的已经不是某个检索算法，而是一个能够重新解释整道题的中心命题：

> **Shopping intent is not a fixed label to detect. It is a changing state jointly formed by the user’s language and the catalog’s response. Retrieval is therefore both an actuator and a sensor.**

换成更适合视频传播的一句话：

> **Most shopping agents retrieve after they understand the user. Ours retrieves to understand the user.**

这个故事的上限很高。它把官方题面中原本较为松散的 Buying/Browsing、Information Accumulation、Intent Override、Over-Generality、Proactive Guidance、Context Distillation 和 Adaptive Orchestration，统一成了一个“持续管理购物意图不确定性”的控制问题。官方 Track 4 确实把这些能力、混合检索、LLM ranking 以及 Hit@10、MRR、MTTC 放在同一个问题中，并采用 Technical Execution 35%、Innovation 20%、Impact 20%、Feasibility 15%、Presentation 10% 的评价结构。

但目前代码真正完整证明的是：

```text
Probe retrieval
→ 估计 T_t / D_t
→ 改变 recall breadth、route budget 和 ranking diversity
```

尚未完整证明的是：

```text
Probe retrieval
→ 选择当前最有价值的系统动作
→ 提出由候选空间导出的澄清问题
→ 用户意图发生收缩、扩展或改写
→ 下一轮重新 sensing
```

因此我对项目的核心判断是：

* **Problem Insight：决赛级，甚至是争冠级。**
* **工程深度：显著超过普通 72 小时 hackathon 项目。**
* **检索与排序实现：较完整。**
* **“Retrieval as Sensing”闭环：完成了 sensing 和 retrieval adaptation，但 guidance/control 还差最后一段。**
* **长期记忆：现在只是接口和 contract，不应作为已完成能力宣传。**
* **当前最大风险不是代码不够，而是故事承诺比实现领先半步，而且材料太多、主线不够压缩。**

# 二、双轨策略是正确的，但不能叫“刷分算法与真正算法”

## 1. 当前隔离方式本身很干净

`starter/agent.py:38–80` 明确规定：

```python
Agent()
```

默认构造 `official_simulator` 的确定性策略，而：

```python
Agent(mode="real_world", deepseek_api_key="...")
```

才构造完整 Capability Mode。两个模式：

* 使用同一官方 API；
* 不根据 evaluator、sample ID、prompt 特征或 target 信息暗中切换；
* 配置互斥；
* real-world 依赖不存在时 fail fast；
* 不会静默降级到 toy 模式。

这是一个好的工程边界。它不是 evaluator detection，也不是隐藏规则，而是显式的运行产品配置。

## 2. 对外应该这样命名

不要在 Devpost、README 或视频中使用：

* score-hacking mode；
* toy exploit；
* 刷分模式；
* “官方环境背离题意，所以我们另外做了一个真的”。

建议统一为：

### Benchmark Compatibility Path

> A deterministic, API-free path optimized for protocol reliability under the organizer’s reproducible simulator.

### Product Capability Path

> A catalog-grounded adaptive shopping system implementing Retrieval as Sensing.

关键解释是：

> The benchmark protocol measures a constrained observable slice of conversational commerce. We isolate benchmark-specific compatibility rather than contaminating the product architecture with simulator assumptions.

这样既承认官方 evaluator 的重要性，也解释了为什么产品架构没有被模板语言牵着走。

## 3. Benchmark Mode 的完成度很高

仓库中的独立 review artifact 给出了：

| Evaluation                | Sessions | Hit@10 |      MRR |  MTTC | TechnicalScore |
| ------------------------- | -------: | -----: | -------: | ----: | -------------: |
| Public `typed_first`      |      200 | 1.0000 | 0.942506 | 2.810 |   **0.946552** |
| Public `other_first`      |      200 | 0.9950 | 0.930214 | 2.590 |   **0.944764** |
| Bundled unseen seed       |     2000 | 0.9940 | 0.943333 | 2.697 |   **0.946060** |
| Reviewer-independent seed |     2000 | 0.9895 | 0.943227 | 2.738 |   **0.942958** |

它的优点包括：

* 不读取 evaluator target；
* 不导入 evaluator；
* 不访问公开标签或行为卡；
* 不硬编码 ASIN；
* 只根据 catalog 和对话输入工作；
* 独立 2000-session stress 仍保持接近 99% Hit@10。

因此作为 **simulator-specific deterministic baseline**，它非常强，完成度大约在 **92%–96%**。

但它依赖官方 simulator 会披露 catalog 中近乎原样的 feature/detail phrase，天然不适合真实用户表达。视频中只应把它作为“protocol reliability proof”，不要让它成为产品故事主角。

# 三、Capability Mode 的代码质量：真正强的部分在哪里

完整路径大致是：

```text
User utterance
    ↓
DeepSeek reconcile_session_intent tool call
    ↓
Deterministic planner / reducer / validation
    ↓
Typed Session Context
    ↓
Query Compiler
    ↓
Probe + Fuzzy Intent Volume
    ↓
T_t: intent transparency
D_t: evidence health
    ↓
Hard-mask-first multi-route retrieval
Dense + Lexical + Facet + RRF
    ↓
BGE shortlist
    ↓
DeepSeek candidate judgements
    ↓
0.8 DeepSeek + 0.2 BGE
    ↓
T-aware DPP
    ↓
Deterministic evidence-bound response
```

这不是简单的“LLM 套搜索”，架构上已经相当成熟。

## 1. DeepSeek 原生 tool call 与 typed memory 是一个很好的子故事

Query Understanding 强制 DeepSeek 调用：

```text
reconcile_session_intent
```

它不是让模型直接编辑 Python object，也不是把完整聊天历史无限塞回 prompt。模型提交“本轮结束后的完整意图框架”，然后本地代码通过 planner/reducer 生成和校验：

* `AddPreference`
* `ReplaceFacet`
* `RemovePreference`
* `ClearFacet`
* `SetDontCare`
* `SwitchGoal`

这个设计的真正价值是：

> **LLM interprets; deterministic code commits.**

因此宣传时不要说：

> DeepSeek directly operates our memory.

应该说：

> DeepSeek proposes a typed memory transition through a native tool call; a deterministic reducer validates and commits it.

这是比“LLM 自动维护记忆”严谨得多的工业表达。

现有自然语言固定测试中：

* 130/130 Query Understanding 成功；
* 130 次均一次 function call 完成；
* 0 repair；
* 0 pipeline error；
* 127 个可检索状态进入 compiler/probe；
* 3 个首轮被合理判定为暂不可检索；
* 收紧 33/33；
* 放宽 10/10；
* 稳定 7/7；
* 三轮渐进收紧 20/20。

这个证据较强，但仍属于固定内部语料，而不是独立 held-out。报告中应写成“fixed-suite protocol reliability”，不要写“泛化准确率 100%”。

## 2. Intent Transparency 的数学定义是可解释的

目前的：

$$
T_t
=
1-
\frac{\log(1+N_t)}
{\log(1+N_{\text{catalog}})}
$$

其中 \(N_t\) 是经过：

* hard constraints；
* semantic preference Product of Experts；
* duplicate-density discount；

之后剩余的有效 intent volume。

因此要特别明确：

> **\(T_t\) 不是“模型有 83% 把握理解了用户”。**

它表达的是：

> **在当前 catalog 中，满足当前意图的有效商品空间有多集中。**

* 高 \(T_t\)：可行商品空间较小、较集中；
* 低 \(T_t\)：可行商品空间较大、较开放。

而 \(D_t\) 用于表示：

* 证据是否充足；
* hard facet 是否有足够 catalog support；
* 当前数值是 healthy、degraded 还是 unavailable。

这个二元设计比单独做“意图置信度”专业很多。

## 3. \(T_t\) 已经真正改变 candidate generation，而不只是改最终权重

`transparency_recall.py` 当前实现了：

$$
M(T)=1+\operatorname{round}((1-T)\cdot5)
$$

即：

| \(T_t\) | 请求 semantic directions |
| ------: | ---------------------: |
|    0.00 |                      6 |
|    0.25 |                      5 |
|    0.50 |                      4 |
|    0.75 |                      2 |
|    1.00 |                      1 |

300 个 candidate slots 也随 \(T_t\) 动态分配：

| \(T_t\) | Dense | Lexical | Facet |
| ------: | ----: | ------: | ----: |
|     0.0 |   210 |      45 |    45 |
|     0.5 |   180 |      60 |    60 |
|     1.0 |   150 |      75 |    75 |

这非常重要，因为它说明：

* 低透明度不只是“最后多放几个不同商品”；
* 系统从召回阶段就探索更多 catalog-grounded semantic directions；
* 高透明度才向 lexical、facet 和精确匹配收缩。

在 Hokkaido winter case 上，原先 1 个方向、4 个 group，变成 6 个方向、7 个 group；固定 query 的 causal sweep 也呈现 `6, 5, 4, 2, 1`。这是可以直接放进视频的核心证据。

## 4. T-aware DPP 的行为是合理的

冻结 quality scores，只改变最终 T-aware DPP：

| Case                  | \(T_t\) | Quality Top-10 cosine | DPP Top-10 cosine | 原 Top-10 保留 |
| --------------------- | ------: | --------------------: | ----------------: | ----------: |
| Hokkaido winter       |    0.10 |                0.7842 |            0.7452 |        6/10 |
| Red wedding accessory |    0.55 |                0.7298 |            0.7160 |        9/10 |
| Black snow boots      |    0.90 |                0.7569 |            0.7569 |       10/10 |

也就是：

* 模糊时显著改变 slate；
* 中等时轻微调整；
* 明确时保持质量排序。

这比固定 diversity coefficient 更容易向评委说明，也很好地对应 Exploration–Exploitation。

## 5. Ranking 的 contract 和 fallback 路径设计得很好

当前 ranking path：

```text
300 candidates
→ BGE direction-protected shortlist, default 48
→ DeepSeek submit_candidate_judgements
→ application validation
→ optional one repair
→ BGE fallback
→ formal MMR fallback
```

Prompt 中也明确区分：

* matched；
* unsupported；
* conflict；

并规定：

> Unknown evidence is unsupported, not a confirmed conflict.

这一点很工业化，能避免商品 metadata 缺失时把“没写”误判成“不满足”。

不过目前 `strict_tools=False`。因此准确表述是：

> Native forced tool calls with application-enforced schema validation and one repair attempt.

不要宣传成 DeepSeek provider 自身的 strict-schema mode。

# 四、目前最关键的不足：感知之后没有真正做“最佳动作选择”

这是当前故事与实现之间最大的断层。

## 1. `SearchBelief` schema 已经存在，但运行时始终没有写入

你们已经设计了非常适合 Retrieval as Sensing 的结构：

```python
SearchBelief(
    based_on_intent_version,
    certainty,
    certainty_method,
    certainty_evidence,
    candidate_modes,
    facet_stats,
)
```

其中：

* `candidate_modes` 可以表示候选的几个主要方向；
* `facet_stats` 已有 entropy、coverage、top_values；
* 还绑定 intent version 和 probe evidence。

但 `FullPipelineOtherAgent._advance_context()` 当前始终写：

```python
search_belief_probe_id=None
search_belief=None
```

运行时只是把上一轮 `IntentTransparencyEstimate` 保存在：

```python
session.previous_transparency
```

这意味着：

> Probe 的结果现在是一个 audit 中的临时指标，而不是 Session Context 中正式、可版本化的环境观察。

从故事上看，这是很伤的。因为你们说 retrieval 是 sensing，但 sensing 的 observation 没有进入 state。

### 建议

每轮 probe 后生成：

```python
SearchBelief(
    based_on_intent_version=intent.version,
    certainty=T_t,
    certainty_method="fuzzy_intent_volume_v1",
    certainty_evidence=...,
    candidate_modes=...,
    facet_stats=...,
)
```

同时写入：

```python
search_belief_probe_id=f"{session_id}:turn:{turn}:probe"
```

这会让以下叙事真正成立：

```text
Language state + catalog observation
→ decision state
```

而不只是：

```text
Language state
→ one scalar
```

## 2. \(D_t\) 还没有进入 retrieval controller

代码和文档都明确承认：

> `D_t` health is not yet passed into the recall controller.

当前 controller 只接收：

```python
controller.search(compiled, transparency=T)
```

但以下两种状态意义完全不同：

### 情况 A

```text
T 高，D healthy
```

用户很明确，catalog 也有充分证据。应该收紧。

### 情况 B

```text
T 高，D degraded
```

用户要求非常具体，但 catalog 可能根本没有可靠支持，或者很多 hard facets 在 metadata 中缺失。此时不应继续自信收紧，而应澄清、解释缺口或建议放宽。

建议冻结一个非常容易演示的 2×2 controller：

| Intent Transparency | Evidence Health            | 系统动作                                      |
| ------------------- | -------------------------- | ----------------------------------------- |
| Low \(T\)           | Healthy \(D\)              | `EXPLORE`：多方向、多样性、高价值澄清                   |
| High \(T\)          | Healthy \(D\)              | `NARROW`：强化 filter/lexical、低多样性、集中推荐      |
| High \(T\)          | Degraded \(D\)             | `CLARIFY_OR_RELAX`：说明 catalog gap，询问可放宽约束 |
| Low \(T\)           | Degraded/Unavailable \(D\) | `RECOVER`：改写 query、fallback、避免把检索故障当浏览意图  |

这张表应该成为架构图和视频的中心，而不是 Dense/BM25/BGE 的组件清单。

## 3. unavailable 和 exception 的 fallback 语义目前不一致

运行时代码中：

```python
transparency.transparency is None
→ applied_transparency = 0.0
```

而 estimator 抛异常时：

```python
applied_transparency = 0.5
```

这意味着：

* “明确 unavailable”会被解释成最大探索；
* “实现异常”却被解释成中性值。

这个选择目前没有清楚的 policy 依据。建议不要把 unavailable 偷偷投射到一个正常 \(T\) 值，而是让 ActionPolicy 显式处理：

```python
if status == UNAVAILABLE:
    action = RECOVER_OR_CLARIFY
elif status == DEGRADED:
    ...
```

如果必须给 recall 一个数值，优先：

* 保留上一轮健康 \(T\)；
* 或使用 0.5；
* 同时标记 degraded route；

不要默认为 0.0，因为这会把 measurement failure 误当作真实 browsing。

## 4. 当前问题生成仍然是 generic slot guidance

`DeterministicResponseComposer._follow_up()` 最终主要落到：

```text
Which direction should I narrow first?
Which style or trade-off should I prioritize next?
Is there one remaining detail you want me to treat as non-negotiable?
```

这些问题没有真正来自：

* candidate modes；
* facet entropy；
* top-value split；
* expected candidate reduction。

所以当前系统实际上是：

> T-aware response wording

而不是：

> Retrieval-grounded active clarification

这直接影响你们所说的“最大限度引导购买者拓展和收缩自己的购买意图”。

### 最小可行修补：不需要再引入一个 LLM

你们现有 `SearchBelief.facet_stats` 已足够实现一个简单 VOI planner：

$$
\operatorname{VOI}(f)
=
\operatorname{coverage}(f)
\cdot
H_{\text{norm}}(f)
\cdot
\operatorname{separation}(f)
-
\operatorname{questionCost}(f)
$$

约束：

* 排除已经 hard-constrained 的 facet；
* 排除 `dont_care`；
* coverage 至少约 0.6；
* top values 最好是 2–4 个可理解方向；
* 不问 product metadata 严重缺失的字段。

然后生成：

```python
QuestionPlan(
    facet="style_direction",
    alternatives=("smart-casual loafer", "walking-focused sneaker"),
    expected_information_gain=0.63,
    source_probe_id="...",
)
```

对用户的问题变成：

> Would you prefer something more smart-casual, like a loafer, or more walking-focused, like a clean sneaker?

而不是：

> Which direction should I narrow first?

官方 typed `ask_attribute` 仍然可以保持 `"other"`，自然语言问题放在 `message` 即可。

这一个改动会把你们从“有一个不确定性指数”提升到：

> **The agent asks questions selected from the structure of the current product space.**

这才是真正的 Retrieval as Sensing。

# 五、长期记忆：现在必须降级为 roadmap，而不是 live feature

代码中的：

```python
class RankingUserProfile:
    """Versioned opaque envelope owned by the future long-term-memory module."""
```

已经直白地说明它属于 future module。

虽然：

```python
RealWorldRankingCoordinator.rank(..., user_profile=None)
```

支持可选 profile，ranking prompt 也规定：

> Current session intent is authoritative; long-term profile is secondary.

但真实 runtime 调用 `rank()` 时没有传入 `user_profile`。现在存在的是：

* `ProfilePrior`；
* raw reset profile；
* optional ranking contract；
* profile precedence 规则；
* 一个冲突 profile 的组件 smoke test。

缺少的是：

* 跨 session 持久化；
* distillation；
* confidence/version/TTL；
* consent；
* profile merge；
* stale preference eviction；
* runtime injection；
* profile A/B 证据。

因此宣传时建议严格区分：

| 能力                                   | 当前状态        | 可否作为主卖点            |
| ------------------------------------ | ----------- | ------------------ |
| Session memory 与 override            | 已实现         | 可以                 |
| Profile prior envelope               | 有 contract  | 可以作为 extensibility |
| Profile injection into final ranking | 未接通 runtime | 暂时不可以              |
| Long-term memory distillation        | 未实现         | 只能 roadmap         |
| Cross-session personalization        | 未证明         | 不可以                |

提交前不建议临时实现完整长期记忆。它的产品治理问题比代码本身更大。最高性价比是：

1. 把 reset 的 profile 转换成 `RankingUserProfile`；
2. 传入 ranking；
3. 做一个 current-session override wins 的受控 A/B；
4. 把它称为 **profile injection**；
5. 把 distillation 画成虚线 roadmap。

优先级仍低于 SearchBelief、\(D_t\) controller 和 VOI question。

# 六、工程与可复现性方面的实际风险

## 1. 产品 runtime 目前位于 evaluation script

`real_world.py:237–259` 动态导入：

```python
scripts.simulator.evaluate_full_pipeline_other
```

并实例化其中的 `FullPipelineOtherAgent`。

也就是说，真正的产品 orchestrator 位于一个 1700 多行的 simulator evaluation script 中。功能能够工作，但边界不符合你们“成熟产品架构”的叙事。

应移动到：

```text
src/shopping_copilot/application/runtime_agent.py
```

evaluation script 只负责：

* fixture；
* simulator adapter；
* metric collection；
* report generation。

这是小改动，却能显著提高 Technical Design 的可信度。

## 2. 默认离线模式没有真正做到依赖隔离

`starter/agent.py` 顶层导入：

```python
from shopping_copilot.application import ...
```

而 `application/__init__.py` 又 eagerly import real-world、quality ranking、response generation 等模块；顶层 `shopping_copilot/__init__.py` 也 eagerly import 多个子包。

在没有安装 runtime lock 的干净环境中：

```python
from starter.agent import Agent
```

会立即要求 `rfc8785`。

这不一定是安装后的运行错误，但与 README 中“starter uses only Python standard library”的表述有冲突。那个说法对于独立 minimal runnable archive 可能成立，对当前 integrated root 不成立。

两个解决方案：

* 真正做 lazy import，让 `Agent()` 只导入 toy 所需依赖；
* 或明确区分“minimal benchmark submission package”和“full research repository”。

第一种更好。

## 3. Capability Mode ZIP 当前不可直接复现

除了缺少 catalog 外，还缺 release/index/density artifacts。并且配置默认：

```python
device="cuda"
local_files_only=True
```

这会导致没有预缓存模型或没有 CUDA 的评委环境无法运行。

最低要求是提供：

```text
python scripts/prepare_demo.py
python scripts/run_demo.py --mode real --device auto
python scripts/run_demo.py --mode replay
```

其中：

* `real`：有 key 和 artifacts 时真实运行；
* `replay`：播放一次真实保存的 audit，用于稳定展示；
* `device=auto`：CUDA 不可用时回落 CPU；
* README 明确下载/构建每个 artifact 的命令和预计时间。

Replay 必须标注：

> Recorded from a real end-to-end run.

不要把静态伪造数据伪装成 live run。

## 4. 现在还不能宣传“commercial efficiency”

现有 DeepSeek ranking smoke：

| Case                  |       Cards | Accepted-call tokens | DeepSeek latency |
| --------------------- | ----------: | -------------------: | ---------------: |
| Hokkaido winter       |          48 |               19,272 |           23.4 s |
| Red wedding accessory |          48 |               20,519 |           28.3 s |
| Black snow boots      | 29，含 repair |               13,984 |           46.4 s |

检索 warm latency只有约 0.10–0.42 秒，但完整 quality ranking 的 20–46 秒不适合正常 conversational commerce。controller 初始化也约 95 秒。

报告中应承认这是：

> High-quality showcase path, not the final serving configuration.

然后给出明确 production cascade：

```text
Cheap deterministic retrieval
→ BGE shortlist
→ invoke quality LLM only when expected decision value exceeds cost
→ cache product evidence/judgements
→ dynamic shortlist size
→ BGE-only fallback
```

最容易实现的是让 shortlist 随 \(T_t,D_t\) 改变：

* 高 \(T_t\)、healthy：16–24 cards；
* 低 \(T_t\)：保留 32–48 cards；
* degraded：不一定值得调用昂贵 ranker；
* repeated query：复用 product judgement cache。

视频里一定要显示真实 latency/token，而不是把等待剪掉后让人以为是 300ms。

# 十四、技术报告应如何组织

## 推荐标题

> **Retrieval as Sensing: Catalog-Grounded Intent Transparency for Adaptive Conversational Commerce**

## 1. Abstract

只回答四件事：

1. 传统系统把意图当固定标签；
2. 你们把它视为变化状态；
3. probe 得到 \(T_t,D_t\)，控制 recall/rank/question；
4. 给出最重要的三组结果。

## 2. Problem Reframing

区分：

```text
Classify intent
```

和：

```text
Manage preference uncertainty over time
```

强调 Buying/Browsing 是连续状态空间中的区域，不是两类用户。

## 3. Formalization

建议冻结以下符号：

$$
S_t = \text{typed session intent}
$$

$$
O_t = \operatorname{Probe}(S_t,\mathcal C)
$$

$$
(T_t,D_t)=g(O_t,S_t)
$$

$$
a_t=\pi(S_t,T_t,D_t)
$$

$$
R_t=\operatorname{Retrieve}(\mathcal C,S_t,a_t)
$$

$$
q_t=\arg\max_f \operatorname{VOI}(f\mid O_t,S_t)
$$

然后：

$$
S_{t+1}
=
\operatorname{Reduce}(S_t,\text{user feedback to }R_t,q_t)
$$

这是整篇报告的骨架。

## 4. Typed State and Native Tool Contracts

说明：

* complete-state reconciliation；
* deterministic reducer；
* versioning；
* intent override；
* current session overrides profile；
* model不能直接写 store。

## 5. Retrieval as Sensing

包括：

* hard-mask；
* structured/semantic Product of Experts；
* density correction；
* intent volume；
* \(T_t\) projection；
* \(D_t\) diagnostics；
* unavailable semantics。

不要把 \(T_t\) 写成 confidence。

## 6. Adaptive Retrieval and Ranking

说明：

* multi-center；
* direction count；
* route budgets；
* BGE protected shortlist；
* DeepSeek individual judgement；
* DPP 的 slate objective；
* repair/fallback。

## 7. Adaptive Guidance

这是报告中必须新增的一节：

* ActionPolicy 2×2；
* candidate modes；
* facet entropy；
* VOI question；
* expand/narrow/relax/recover。

没有这节，论文标题中的 Retrieval as Sensing 会显得只是在给 retrieval tuning 换名字。

## 8. Dual Execution Paths

画清楚：

```text
Shared Agent API
├── Benchmark Compatibility Path
└── Product Capability Path
```

解释隔离原因、各自目标和不能互相外推的指标。

## 9. Evaluation

建议分为四层：

### 9.1 Official simulator

Benchmark Mode 的 public metrics。

### 9.2 Independent simulator stress

2000 unseen synthetic sessions，并说明 synthetic bias。

### 9.3 Real-catalog component evaluation

* 方向数 sweep；
* DPP；
* QU；
* hard compliance；
* failure fallback。

### 9.4 End-to-end capability cases

展示完整对话，不一定硬套官方 purchase target。

## 10. Ablations

最低必须有：

| Ablation                           | 目的                        |
| ---------------------------------- | ------------------------- |
| Fixed \(T=0.5\) vs dynamic \(T_t\) | 证明 sensing 值得存在           |
| \(T_t\)-only vs \(T_t+D_t\)        | 证明 evidence health 的必要性   |
| Single-center vs multi-center      | 证明 broad exploration      |
| No DPP vs T-aware DPP              | 证明 slate adaptation       |
| Generic vs VOI question            | 证明 proactive guidance     |
| No typed reducer vs typed reducer  | 证明 override/state safety  |
| DeepSeek path vs BGE fallback      | 证明 quality/cost trade-off |

最关键的 outcome 不一定是官方 Hit@10，可以先测：

* next-turn intent-volume reduction；
* candidate entropy reduction；
* useful answer rate；
* hard-constraint preservation；
* number of turns to reach healthy high \(T\)；
* latency/token。

## 11. Failure Analysis

至少写：

* product metadata missing；
* high \(T\), degraded \(D\)；
* impossible conjunction；
* DeepSeek malformed output；
* timeout/rate limit；
* repeated semantic preference；
* goal switch；
* unavailable probe；
* observationally identical simulator products。

## 12. Feasibility

必须有表：

| Stage            | Cold latency | Warm latency |  Tokens | Fallback     |
| ---------------- | -----------: | -----------: | ------: | ------------ |
| QU               |            … |            … |       … | retain/retry |
| Probe            |            … |       ~94 ms |       0 | unavailable  |
| Retrieval        |   ~95 s init |  0.10–0.42 s |       0 | formal route |
| BGE              |            … |            … |       0 | formal MMR   |
| DeepSeek ranking |            — |      23–46 s | 14k–20k | BGE DPP      |

然后提出 dynamic cascade，而不是只写“以后优化”。

## 13. Limitations

主动承认：

* \(T_t\) 参数在同一固定语料上选择，不是独立 calibration；
* direction correctness 部分来自状态代数；
* hard-facet simultaneous compliance 仍有限；
* real shopping conversion 没有 ground truth；
* official simulator 不建模 preference formation；
* LLM ranking 目前延迟和 token 较高；
* long-term memory distillation 尚未实现；
* capability package 仍需 artifact preparation。

这不会让项目显得弱，反而会让评委相信你们知道系统边界。

# 最终判断

你们最接近高排名项目的部分不是 DeepSeek tool call，也不是 DPP，而是这个 reframe：

> **The query is not merely incomplete. It is evolving.**

更完整地说：

> **Intent transparency is a relation between the current user state and the geometry of the available catalog. Retrieval therefore serves two roles: finding products and observing the remaining decision space.**

这是足以让评委记住的主张。

但现在代码仍然像：

```text
A very rigorous adaptive retrieval and ranking system
with an excellent uncertainty narrative
```

完成 SearchBelief 持久化、\(T_t/D_t\) ActionPolicy 和 probe-grounded question planner 后，它才会真正变成：

```text
A shopping agent that senses the product space
and actively helps the user form a decision
```

**我的最终评级是：核心 insight 已达到争冠级；当前 package 是有力的 Finalist 候选；距离稳定 Top 3 主要差一个可见的 closed control loop、一个可一键复现的 Capability Mode，以及一支能在三分钟内把所有复杂度压缩成单一用户旅程的视频。**
