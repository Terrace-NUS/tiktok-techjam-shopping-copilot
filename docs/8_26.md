# 核心修正

你的判断是对的。我需要修正上一轮的主线：

> **Constraint Fingerprint、`ask_attribute="other"`、针对 metadata 模板的精确匹配，都只能是 TechJam evaluator 的兼容层；不能成为项目的技术核心。**

真正值得作为项目核心的，应当是：

> **一个证据驱动、状态可验证、会根据检索反馈选择“直接搜、改写、澄清或推荐”的自适应购物控制器。**

换句话说：

* local evaluator 是 **ABI、回归测试和最低性能门槛**；
* private TechnicalScore 是重要结果，但不是完整项目目标；
* 真正的项目应证明：系统能在模糊需求、逐步披露、偏好覆盖、长期偏好冲突和不同检索失败模式下，自主改变工作流。

官方 specification 自己其实已经把“创新方向”写得比 evaluator 更完整：结构化状态、动态上下文、问题价值估计、安全个性化、失败检测、策略切换、低延迟、透明解释都在明确鼓励范围内。

# 一、先明确“真正的评分标准”

## 1. 当前官方材料存在一个必须正视的冲突

Track 4 problem statement 写的是：

* Technical Execution：35%
* Innovation & Problem Insight：20%
* Impact & Relevance：20%
* Feasibility & Practicality：15%
* Presentation & Communication：10%

并同时列出 HR@K、MRR、MTTC 三个机器指标。

但截至 **2026 年 8 月 26 日**，Devpost Official Rules 写的是：

* Stage Two 使用四项 **等权**标准；
* Technical Execution；
* Innovation & Problem Insight；
* Feasibility & Practicality；
* Impact & Relevance；
* 没有单列 Presentation；
* 若 Official Rules 和其他 TechJam 材料冲突，以 Official Rules 为准。([TikTok TechJam 2026][1])

更重要的是，Official Rules 明确说 judges **不一定实际运行项目**，可以只根据文字、图片和视频评判。([TikTok TechJam 2026][1])

因此，目前最安全的判断是：

| 层次                     | 应如何看待                                                   |
| ---------------------- | ------------------------------------------------------- |
| Private TechnicalScore | 技术能力的必要证据，很可能影响 Technical Execution，但官方没有公开它如何线性映射到最终分数 |
| 四项人工评审                 | 当前 Formal Rules 下真正决定 Stage Two 排名的标准                   |
| 视频与 README             | 虽未必单独计 10%，但它们可能是 judges 获取所有技术证据的唯一渠道                  |
| Local 200 sessions     | 开发回归集，不是能够支撑“真实购物智能”结论的 benchmark                       |

所以你们不能把路线定成：

> “我们在 200 条 deterministic simulator 上刷到了 SOTA。”

正确说法应当是：

> “我们同时在官方兼容评测和更严格的设计意图评测上验证了系统；官方分数证明兼容性，shadow benchmark 和消融证明架构价值。”

---

## 2. Local evaluator 确实只是一个 compatibility toy

它把商品的前几个 `features/details`、正则检测到的颜色和材质、价格拼成 hidden intent；前两个成为 hard constraints，后两个成为 soft preferences。Intent Override 固定在第 3 或第 4 轮，用模板表达“忽略之前偏好”；`ask_attribute="other"` 可以返回任意尚未披露的两个约束。

它几乎没有测试：

* 自然语言中的含蓄约束和复杂否定；
* 多个可接受商品，而非唯一 target ASIN；
* 真实 browsing 中的替代品、组合权衡和探索；
* 问题是否自然、是否回答得了；
* profile 与当前 session 的冲突；
* 跨 session 的 profile 更新；
* 状态摘要是否逐渐漂移；
* 用户耐心、放弃和认知负担；
* 不同检索失败原因需要不同补救策略；
* 线上模型、网络或工具失败。

官方 specification 也明确承认：这些消息是由商品 metadata 的 hidden intent card 模拟出来的，并非原始数据中的真实购物对话。

因此它更像：

> 一个用于验证 Agent API、基础状态机、Exact-ASIN 检索和基本策略的 deterministic unit test。

# 二、题目真正要求的是一个部分可观测的闭环决策系统

与其理解成“RAG 聊天机器人”，更适合把它建模为一个轻量 POMDP：

### 隐变量

* 当前任务意图：Buying / Browsing / 混合；
* 当前有效硬约束；
* 当前软偏好；
* 用户未表达的潜在需求；
* 哪些历史偏好已经失效；
* 用户耐心；
* 当前候选集合中真正的答案。

### 可观测量

* 当前用户消息；
* 已确认的结构化状态；
* profile；
* 每条 retrieval route 的结果；
* Top-K 分数分布；
* route 之间的分歧；
* 候选商品的属性分布；
* 历史问题是否有效。

### 可选择动作

$$
a_t \in
\{
\text{direct retrieve},
\text{rewrite},
\text{clarify},
\text{retrieve+rerank},
\text{recommend}
\}
$$

### 优化目标

不仅是 target hit，还包括：

* 候选覆盖；
* 排名；
* 约束满足；
* 轮数；
* 用户认知负担；
* token 和延迟；
* 状态冲突；
* 策略失败后的恢复。

这正好统一了题面中的所有词：

| 题面语言                   | 实际系统含义                       |
| ---------------------- | ---------------------------- |
| Intent Routing         | 选择当前检索与交互策略                  |
| Hybrid Pipeline        | 多种 evidence channel 的候选生成与融合 |
| Dynamic State Machine  | 对潜在意图状态做持续更新                 |
| Proactive Guidance     | 为减少不确定性而主动获取信息               |
| Context Distillation   | 只把当前决策需要的状态编译进上下文            |
| Adaptive Orchestration | 根据检索反馈重新选择下一步动作              |
| MTTC                   | 对信息获取动作施加交互成本                |

# 三、我建议的核心架构

可以暂时称作：

## Evidence-Grounded Adaptive Shopping Controller

```text
                 ┌────────────────────────────┐
User message ──►│ Turn / Constraint Parser   │
                 │ 只提出结构化状态变更        │
                 └─────────────┬──────────────┘

                 │ ADD / REPLACE / DELETE     │

                 └─────────────┬──────────────┘
                               │
               ┌───────────────▼────────────────┐
               │ Event Ledger + Current State   │
               │ active / superseded / dont-care│
               │ provenance / confidence / scope│
               └───────────────┬────────────────┘
                               │
                 ┌─────────────▼──────────────┐
                 │ Context Compiler           │
                 │ 编译当前有效决策上下文       │
                 └─────────────┬──────────────┘
                               │
                 ┌─────────────▼──────────────┐
                 │ Cheap Probe Retrieval      │
                 │ 诊断当前检索结果             │
                 └─────────────┬──────────────┘
                               │
                ┌──────────────▼───────────────┐
                │ Strategy Controller          │
                │ direct / rewrite / clarify   │
                │ retrieve / rerank / recommend│
                └──────────────┬───────────────┘
                               │
      ┌────────────────────────┼────────────────────────┐
      │                        │                        │
┌─────▼─────────┐      ┌───────▼────────┐      ┌────────▼───────┐
│ Structured     │      │ BM25F / Phrase │      │ Dense Semantic │
│ Filters        │      │ Retrieval      │      │ Retrieval      │
└─────┬─────────┘      └───────┬────────┘      └────────┬───────┘
      └────────────────────────┼─────────────────────────┘
                               │
               ┌───────────────▼────────────────┐
               │ Candidate Evidence Table       │
               │ route ranks / matched facts    │
               │ conflicts / price / category   │
               └───────────────┬────────────────┘
                               │
               ┌───────────────▼────────────────┐
               │ Constraint Gate → LTR/Reranker │
               └───────────────┬────────────────┘

                │ Memory write gate + trace  │
                └─────────────────────────────┘
```

这里的核心创新不是某个 embedding model，而是：

1. **状态变更是可验证的操作，不是聊天摘要。**
2. **系统先观察检索结果，再决定要不要澄清或改写。**
3. **问题、检索、排序共享同一个 candidate evidence table。**
4. **长期偏好和本次购买约束严格分离。**
5. **所有决策都能解释“为何选择这条 workflow”。**

# 四、逐条对应题目设计意图

## I-A. Dual-Track Routing：不要做硬二分类

题目说 Buying 用高精度 filter，Browsing 用 diverse dense retrieval。这个方向正确，但实现成：

```text
intent == buying:
    BM25/filter
else:
    dense
```

是过度简化。

用户意图不是静态标签。例如：

> “I need something suitable for an outdoor wedding.”

初始看起来是 Browsing；用户随后说：

> “It must be waterproof, black, under $80.”

它立刻变成高约束 Buying。反过来，Buying 用户也可能在看到候选后重新探索。

### 推荐实现：Soft Strategy Router

路由器输出的不是单一标签，而是：

```text
P(buying)
P(browsing)
retrieval route weights
eligible next actions
```

输入特征包括：

* 已确认 hard constraint 数；
* 是否存在 category；
* query abstractness；
* 首次 retrieval 的 Top-1 margin；
* score entropy；
* 候选类别/品牌/属性 entropy；
* BM25 与 dense 的结果重叠；
* lexical 与 semantic route 的分歧；
* rewrite probe 前后候选变化；
* 当前 turn；
* 上一轮问题是否有效。

2026 年的 **Route, Don’t Guess** 直接研究了这个问题：它比较 direct retrieval、blind rewrite、clarification、result-aware rewrite 和 result-aware clarification。实验中，最难的一组查询能从 result-aware intervention 获益，但简单查询反而会被 intervention 伤害；轻量 router 在接近最佳固定策略质量的同时降低约 30% token 成本。更关键的结论是：**先看 retrieval 结果，再决定改写或澄清，明显优于盲目介入。** ([SIGIR eCom][2])

### 这部分最适合你们直接实现

不需要训练复杂 policy：

* 用规则建立第一版；
* 再用 Logistic Regression 或 XGBoost；
* label 是“该 query/session 上哪种策略带来的最终效用最高”；
* 输入全部是可观测 retrieval signals；
* 不需要 LLM router。

这比用一个 LLM 回答“Buying 还是 Browsing”更稳定、便宜，也更容易解释。

---

## I-B. Multi-Route Retrieval：路线要异质，而不是重复

真正有意义的 route 应该产生不同类型的候选：

### Route 1：Structured Constraint Retrieval

处理：

* category；
* material；
* color；
* size；
* budget；
* gender/department；
* 显式否定条件。

这是 Buying 的主要 high-precision route。

### Route 2：BM25F / Phrase Retrieval

分别保留字段分数：

* title；
* ordered features；
* details key/value；
* category path；
* description；
* store。

上一轮讨论的 Constraint Fingerprint 应放在这里。它负责：

* 适配 local evaluator；
* 捕获 catalog 内的稀有属性短语；
* 保护 exact-ASIN recall；
* 不承担系统的“人工智能叙事”。

### Route 3：Product-Domain Dense Retrieval

优先测试 **BLaIR**。它就是基于 Amazon Reviews 2023 的商品 metadata–language pair 训练，官方仓库公开了代码、checkpoint 和 product-search reproduction scripts，领域匹配度明显高于根据通用 MTEB 排名盲选 embedding。([GitHub][3])

同时可测试一个通用语义模型作为 Browsing route，例如 Qwen3-Embedding；它更可能覆盖：

* occasion；
* style；
* use case；
* cross-category scenario；
* catalog 中没有完全词面重叠的需求。

Qwen3 Embedding/Reranker 和 BGE 的 embedding/reranker 工具链都有官方开放实现；BGE-M3 还支持 dense、sparse 和 multi-vector 表示，但这不意味着本题一定需要同时打开全部通道。([Qwen][4])

### Route 4：Result-Aware Rewrite Retrieval

只有在下面情况才触发：

* BM25 与 dense 都低置信；
* 两条 route 完全不重合；
* candidate category 极度分散；
* query 明显描述场景而非商品；
* rewrite probe 显示候选集合发生有意义变化。

不要每轮改写。Route, Don’t Guess 的结果显示，blind rewrite 和 unconditional clarification 不是普遍最优；result awareness 才是关键。([SIGIR eCom][2])

---

## I-C. Candidate Evidence Table：这是多模块共享的核心数据层

每个进入 union pool 的商品应保留：

```text
parent_asin
BM25 各字段分数与排名
dense 各 view 分数与排名
structured filters 命中情况
matched active constraints
conflicting constraints
matched source text
price distance
category path overlap
profile prior
route agreement / disagreement
```

这样 clarification、routing、ranking 和 explanation 使用的是**同一份可审计 evidence**。

否则容易出现：

* router 认为结果很模糊；
* clarifier 却不知道候选为什么模糊；
* reranker 又根据完全不同的 prompt 排序；
* explanation 最后编一个不对应实际 ranking 的理由。

ProductAgent 是目前最贴近题目整体结构的参考：它维护 structured memory，从当前 candidates 提取属性统计，主动生成澄清问题，并在 symbolic+dense hybrid index 上形成闭环。其 PROCLARE benchmark 使用了 2,000 个自动生成 session。([ACL Anthology][5])

但 ProductAgent 仍然不能直接作为完整答案：

* 它的 override/state supersession 不够强；
* 主要依赖 target-aware simulator；
* 长期 profile 不是重点；
* 我没有核验到可直接运行的完整官方实现。

所以应借它的闭环结构，不应复制它的 simulator 结论。

---

## I-D. LLM Semantic Ranking：LLM 不应拥有最终否决权

推荐 pipeline：

```text
Candidate Union 100–300
        ↓
Deterministic Constraint Gate
        ↓
LightGBM LambdaMART / local scoring
        ↓
Optional Cross-Encoder top 20–50
        ↓
Grounded Explanation
```

### 第一层：Constraint Gate

明确违反硬约束的商品：

* 直接过滤；
* 或施加强惩罚；
* 但低置信解析不能成为 hard filter。

### 第二层：LTR

输入：

* route rank/score；
* exact phrase matches；
* hard/soft constraint coverage；
* conflict count；
* category overlap；
* price distance；
* route agreement；
* state confidence；
* profile prior。

这一步适合 LightGBM LambdaMART，因为：

* 数据量小；
* 结构化特征重要；
* 推理快；
* 能解释 feature contribution；
* 不依赖网络。

### 第三层：小型 semantic reranker

只有 recall 已过关再加入：

* Qwen3-Reranker；
* `bge-reranker-v2-m3`；
* 小型 cross-encoder。

BGE 官方明确将 reranker 用于重排 embedding retrieval 的 Top-K，而不是替代第一阶段检索。([GitHub][6])

### 排名和解释必须分离

非常新的 **Cleo** 提出了透明、可控的 conversational commerce 架构，值得借鉴的是：

* 排名由确定性/可控的属性损失完成；
* LLM 负责对话和基于证据的解释；
* 推荐原因可以追溯到具体属性和代价。

它是 2026 年 8 月的新 preprint，不能当作已被工业验证的标准方案，但非常适合你们的 demo 设计。([arXiv][7])

# 五、Dynamic State Machine：最重要的模块可能不是 retrieval

## 1. 不要保存“对话摘要”，要保存状态操作

推荐状态结构：

```text
Constraint
    namespace
    type
    raw_value
    canonical_value
    polarity
    hardness
    confidence
    provenance
    source_turn
    scope
    status = active | superseded | dont_care
    supersedes
```

LLM 不直接修改状态，只提出操作：

```text
ADD
REPLACE
DELETE
RELAX
CONFIRM
REJECT
```

然后确定性 validator 检查：

* schema；
* value domain；
* 冲突；
* override 目标是否存在；
* hard/soft 权限；
* profile 是否能覆盖显式当前约束；
* 是否需要确认。

## 2. 使用 event sourcing

不要就地覆盖字典：

```python
state["color"] = "blue"
```

而应记录：

```text
Turn 2: ADD color=black
Turn 4: SUPERSEDE color=black
Turn 4: ADD color=blue
```

当前状态是 event log 的 materialized view。

优势：

* 可以解释系统为什么改变；
* 可以恢复误更新；
* 可以计算 stale-slot leakage；
* 可以展示 override；
* cache 可以绑定 `state_version`，用户改口后自动失效。

## 3. 直接参考的研究

**ReacTOD** 将 dialogue state 更新表述为受约束的离散操作，并在模型输出外增加确定性 validator 和自我修正循环。这与本题的 slot accumulation 和 override 高度吻合。([arXiv][8])

**PyTOD** 提供开放仓库，把对话状态/工具行为表示成可执行程序，并使用 execution feedback 纠正错误。它的整个模拟环境没必要移植，但其 parser、Pydantic validation、execution engine 和测试组织方式值得直接读代码。([GitHub][9])

Microsoft 的 **Evolving Intent** 已经开放了数据构造代码，它把静态任务改造成：

* incremental disclosure；
* argument revision；
* function redirection。

这正适合用于生成比官方 Intent Override 更严格的 stress tests。([GitHub][10])

更近期的 **StateMemBench** 明确指出：问题不只是“能否检索到旧记忆”，而是“能否区分当前状态和已经 superseded 的状态”；即使 perfect retrieval，memory system 仍可能执行旧事实。其 StateMem 方法显式建模 supersession 和依赖关系。([arXiv][11])

这意味着：

> 仅把所有历史消息放进长上下文，或者把历史摘要存进 vector DB，都没有真正解决 Intent Override。

# 六、Proactive Guidance：不能固定按颜色、材质、预算轮流问

## 1. Over-Generality 不应定义为 raw candidate count

Retriever 总能返回固定 Top-100，所以“结果有 100 个”本身没有意义。

更合理的诊断信号：

* Top-1 / Top-2 margin；
* score entropy；
* route disagreement；
* category entropy；
* attribute-value entropy；
* 候选与 active constraints 的平均 coverage；
* 有效候选数：

$$
N_{\text{eff}}
=
\exp\left(
-\sum_i p_i \log p_i
\right)
$$

当 \(N_{\text{eff}}\) 很大、margin 很低且存在可回答高价值问题时，才进入 clarify。

## 2. 问题选择应直接优化“预期决策收益”

可以定义：

$$
U(a)=
P(\text{answerable}\mid C,a)
\cdot
\mathbb E[
\Delta \mathrm{MRR}
+
\beta \Delta \log |C|
]
-
\lambda_{\text{turn}}
-
\lambda_{\text{repeat}}
-
\lambda_{\text{cognitive}}
$$

其中：

* `answerable`：当前 catalog/candidate 中是否真的存在这个 facet；
* `ΔMRR`：回答后预期 target rank 改善；
* `Δlog|C|`：候选池缩减；
* turn cost 对应 MTTC；
* cognitive cost 防止问无意义细节。

### D2D

D2D 使用候选商品的属性分布和偏好不确定性，动态决定：

* 问哪个属性；
* 问哪些值；
* 现在问还是推荐。

它在自己的 Amazon-derived 模拟和有限人评中报告了更高 target-finding、更低 abandonment 和更短对话；但这些数值不能直接外推到 TechJam，作者也明确承认 simulator 和人评规模的局限。([arXiv][12])

### SAGE-Agent

SAGE 将 clarification 建模为结构化不确定性下的 expected value of perfect information，适合借用其“问题价值减去交互成本”的形式。当前我没有核验到成熟、可直接集成的完整官方仓库，因此更适合作为算法参考。([arXiv][13])

### RAC

RAC 的核心价值是**问题必须被 corpus evidence 支撑**。它先检索相关内容，再训练模型避免生成数据库中无法回答的问题；官方仓库已经公开。你们无需复现其 DPO 训练，但可以直接借用：

* 从 candidate evidence 生成问题；
* question grounding check；
* 无可区分属性时禁止提问。

([GitHub][14])

## 3. Local evaluator 兼容

真实问题生成器最后通过 adapter 映射成：

```text
material
color
size
style
budget
feature
use_case
other
```

`other` 可以作为兼容 fallback，但不能成为项目创新。当前 evaluator 中它会返回任何未披露约束，因此需要单独报告：

* typed clarification policy；
* open-ended/`other` policy；
* 两者分数差；
* private evaluator 变更时的风险。

# 七、Personalized Context Distillation：不要做“聊天记录总结”

“Personalized Context Distillation”不是一个我能检索到的公认算法名；“Dynamic Context Programming”同样更像出题方的能力标签，而不是一个确定的学术框架。

最合理的工程解释是：

## 1. Session state 和 long-term profile 分离

### Session state

表示当前购买任务：

* 本次预算；
* 本次颜色；
* 当前使用场景；
* 当前 hard constraints；
* 当前 dont-care；
* 当前 intent mode。

### Long-term profile

只保存跨任务稳定偏好：

* 长期喜欢某种版型；
* 稳定价格区间；
* 常购类别；
* 反复出现的材质偏好；
* 需要长期记住的个人事实。

“我要给朋友买一件红色礼物”不能写成“用户长期喜欢红色”。

## 2. Profile write gate

只在下面条件之一满足时写入：

* 用户明确说“以后都……”；
* 多个 session 重复出现；
* 用户显式确认；
* 高置信推断且有多条独立证据。

每条 memory 保留：

```text
fact
scope
confidence
evidence
created_at
last_confirmed_at
status
supersedes
```

当前 session 的显式 hard constraint 永远高于 profile prior。

## 3. Context Compiler

每一轮不拼完整 transcript，而是编译：

```text
current user delta
active session constraints
relevant profile facts
candidate evidence summary
retrieval diagnostics
allowed next actions
```

这才是真正的“context programming”：

> 不是让模型自己修改 prompt 或代码，而是根据当前决策阶段，确定性地构造最小充分上下文。

LangGraph 的 checkpointer/store 划分可以作为工程脚手架：checkpointer 保存 thread-scoped short-term state，store 保存跨 thread 的长期信息。但 LangGraph 本身不是创新，只是减少状态持久化工作。([Docs by LangChain][15])

Amazon 对 Rufus 的公开架构说明也把 account memory、实时商品/价格数据和工具调用区分开：长期用户信息是持久化服务中的记录，而不是简单把全部历史塞回 prompt。([亚马逊网络服务][16])

## 4. 官方 evaluator 无法真正证明这一模块

题面要求长期 user profile，但官方 session 又是 isolated，并且 Agent 只收到安全聚合 profile，没有稳定用户身份和原始跨 session 购买历史。

因此长期 memory 的价值必须通过单独的 cross-session shadow test 和 demo 证明，不能用 local TechnicalScore 冒充证据。

# 八、Adaptive Orchestration：不是多 Agent，而是有限策略控制器

推荐 workflow：

```text
PARSE_DELTA
    ↓
VALIDATE_STATE
    ↓
COMPILE_CONTEXT
    ↓
INITIAL_PROBE_RETRIEVAL
    ↓
DIAGNOSE_RESULTS
    ↓
┌─────────────┬────────────────┬───────────────┐
│ DIRECT      │ RESULT_REWRITE │ CLARIFY       │
└─────────────┴────────────────┴───────────────┘
    ↓
RETRIEVE_AND_FUSE
    ↓
CONSTRAINT_GATE
    ↓
RERANK
    ↓
ASK_OR_RECOMMEND
    ↓
COMMIT_MEMORY_AND_TRACE
```

### 为什么不是多 Agent

这个任务只有几个明确动作和一个小型 catalog。拆成：

* Intent Agent；
* Memory Agent；
* Retrieval Agent；
* Ranking Agent；
* Reflection Agent；

通常只会增加：

* latency；
* token；
* prompt drift；
* failure surface；
* 难以复现的上下游误差。

“Adaptive orchestration”应体现为**策略切换**，而不是“Agent 数量”。

### DSPy 的正确用法

DSPy/GEPA 可以离线优化：

* state extraction prompt；
* query rewrite prompt；
* explanation prompt；
* reranker instruction。

但优化指标必须同时覆盖：

* state correctness；
* retrieval recall；
* question utility；
* token；
* failure rate。

最终 submission 应冻结优化结果，而不是 runtime 自我修改 prompt。DSPy 的官方流程本身也是“给定训练集与 metric，离线搜索更优 program/prompt”。([DSPy][17])

# 九、真正需要建设的是“双评测体系”

## A. Official Compatibility Suite

用途：

* 不允许 TechnicalScore 回退；
* 验证 exact ASIN；
* 验证 API contract；
* 验证 10-turn；
* 验证 Buying/Browsing/Override/Boundary；
* 验证 offline fallback。

保留：

* fingerprint phrase route；
* evaluator-compatible attribute mapping；
* exact metadata retrieval；
* first-hit-aware Top-K policy。

但它只是一组 regression tests。

---

## B. Design-Intent Shadow Benchmark

最值得直接借鉴的是 **EComAgentBench**。

它将 hidden intent 分散在：

* initial query；
* user profile；
* deterministic clarification；

并通过 source-tagged rubrics 和 exact-match 共同评估。公开仓库包含 662 个验证样本以及完整的 generation、prediction、evaluation pipeline。([GitHub][18])

不应该直接使用它的 25 GB product DB；应该把它的 benchmark construction 方法移植到 TechJam 的 50k catalog。

### 建议至少构造八类 shadow scenarios

| 场景                      | 主要测试                                  |
| ----------------------- | ------------------------------------- |
| Precise Buying          | hard constraint locking、exact recall  |
| Open-ended Browsing     | use-case semantic retrieval、diversity |
| Incremental Disclosure  | slot accumulation                     |
| Revision / Override     | supersession、cache invalidation       |
| Negation / Dont-care    | polarity、避免重复提问                       |
| Over-Generality         | question value、candidate reduction    |
| Profile Conflict        | session constraint 是否压过长期 prior       |
| Failure / Degraded Mode | API failure、offline fallback、timeout  |

可以进一步使用：

* Evolving Intent 的 incremental/revision/redirection mutation；
* StateMemBench 的 current/superseded grading；
* D2D 的用户耐心和 abandonment；
* EComAgentBench 的 source-tagged rubrics。

## Shadow metrics

不要再造一个单一“综合 SOTA 分数”。报告 metric vector：

### State

* current-state accuracy；
* stale-slot leakage；
* override recovery turns；
* dont-care repetition rate；
* profile conflict accuracy。

### Retrieval/ranking

* union Recall@100/300；
* conditional MRR；
* hard-constraint satisfaction；
* semantic rubric satisfaction；
* browsing diversity。

### Dialog

* clarification answerability；
* expected vs actual candidate reduction；
* repeated-question rate；
* invalid-question rate；
* turns to confidence threshold；
* simulated abandonment。

### Orchestration

* strategy regret，相对于 per-session oracle；
* unnecessary intervention rate；
* rewrite success rate；
* clarification success rate；
* fallback activation accuracy。

### Engineering

* p50/p95 latency；
* model calls；
* prompt/completion tokens；
* peak memory；
* network-off score；
* failure recovery rate。

# 十三、每个模块的“留或删”判据

这能防止架构为了看起来复杂而膨胀。

| 模块               | 保留条件                                            | 反证条件                              |
| ---------------- | ----------------------------------------------- | --------------------------------- |
| Dense route      | 提高 Browsing/paraphrase 的 union Recall@100       | 与 BM25 union 几乎相同或引入大量冲突商品        |
| Strategy router  | 降低相对最佳固定策略的 regret                              | 不优于固定 direct/result-aware rewrite |
| Clarification    | 回答后实际提高 rank 或降低有效候选数，且抵消 turn cost             | 只增加 MTTC，没有 rank/coverage 改善      |
| Profile          | cross-session rubric 提升且 stale-state error 不增加  | 只在 public simulator 上看似有效         |
| Reranker         | target 已在 candidate union 时显著提高 conditional MRR | recall 不足或 p95 延迟过高               |
| LLM parser       | state accuracy 明显优于规则且输出可验证                     | 结构化字段足够，规则已同等稳定                   |
| Extra retriever  | route union recall 有独立增益                        | 结果高度重叠，只增加工程复杂度                   |
| Long-term memory | 能正确处理 confirmation、scope 和 supersession         | 只是摘要历史后做向量召回                      |

# 最终判断：进入 Final 的三大胜负手

## 1. State correctness，而不是 chat history

你们需要成为少数能明确展示：

* 当前偏好；
* 已被覆盖的偏好；
* profile prior；
* 本次任务约束；
* 每次状态变化的证据；

的队伍。

Intent Override 不应只是 benchmark 的 15%，而应成为你们证明系统真的理解动态用户意图的关键场景。

## 2. Result-aware selective strategy controller

大多数队伍会做：

> classify → retrieve → rerank → ask fixed question。

你们应该做：

> retrieve a cheap probe → diagnose failure → choose direct/rewrite/clarify → retrieve again → decide whether recommendation is worth issuing。

这同时符合：

* adaptive orchestration；
* runtime agility；
* proactive guidance；
* MTTC；
* feasibility；
* token efficiency。

## 3. 双重证据：官方分数 + shadow benchmark

最终证据链应当是：

> Official TechnicalScore 没有牺牲
> → Exact candidate recall 足够
> → Shadow benchmark 中 override、negation、profile conflict 和 browsing 明显更稳
> → 消融能解释提升来自哪个模块
> → 网络断开仍能运行
> → Demo 能看到状态、路由和候选证据如何变化。

---

# 最适合三分钟视频的场景

一个 session 足够：

1. 用户提出模糊、跨类别的场景需求；
2. 首次 retrieval 显示 route disagreement 和高 candidate entropy；
3. controller 没有盲目推荐，而是选择一个 grounded high-value question；
4. 用户回答后候选池显著收缩；
5. 用户突然改口；
6. UI 明确把旧 constraint 标为 `superseded`；
7. context version 变化、旧 candidate cache 失效；
8. routing weight 从 browsing dense 转向 structured buying；
9. target 从候选外进入 Rank 1；
10. 最终解释逐项引用实际商品 metadata，而不是 LLM 自由编造。

这个 demo 同时覆盖四个 pillar，也远比展示“多个 Agent 正在讨论该推荐什么”更有技术说服力。
